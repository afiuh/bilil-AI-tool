# bili_tool 架构优化方案 — 5池并行发现系统

## 一、当前核心问题

管道最终只产出 3-4 条合格视频，远低于期望的 10 条。

### 数据溯源

上一轮完整管道数据链路：

```
发现(173条) → L1(砍149) → L2(砍14) → L3(砍6) → 策展(保留4)
```

| 瓶颈 | 表现 | 根因 |
|------|------|------|
| 发现质量差 | 173 条中 88 条来自音乐分区(VOCALOID/翻唱/MV)，人均历史仅 20 条 | 核心数据源全空，靠话题关键词+硬编码分区硬撑 |
| L2 一刀切 | 24→10，cutoff 0.4 太狠 | 无字幕视频 L2 天然低分被误杀 |
| L3 再砍 | 10→4 | 合格候选本身就不够 |
| 无兜底 | 不够 10 条就接受，塞低质 | 没有重试机制 |

### 核心数据源状态

| 数据源 | 实际存量 | 当前用途 | 
|--------|---------|---------|
| 关注的 UP 主 | 141 人 | ❌ 仅用做排除（不推荐他们），未做种子 |
| 自建收藏夹 | 10 个 | ❌ 未接入 |
| 关注合集 | 30 个 | ❌ 未接入 |
| UP主权重 | 0 条 | ❌ 空，策略1(UP主蔓延)无种子可爬 |
| 候选BV号 | 0 条 | ❌ 空，策略2(关联推荐)无种子 |
| 历史/投币 | — | 不参考（用户明确排除） |

**结论**：四策略中两策略因种子为空直接废掉，只剩关键词搜索和分区探索硬撑。这是产出不足的根本原因。

## 二、解决方案：5池并行发现系统

### 2.1 核心思路

将单一发现管道拆为 5 个独立池，各池锁定一个 B 站分区独立运作，并行搜索、独立筛选，最终合并输出。

### 2.2 分区分配策略

每次运行时从分区白名单中随机抽取 5 个分区，分配黑名单永久排除低质分区。

**分区黑名单**（永久排除）：
- 音乐综合、VOCALOID·UTAU、翻唱、MV、电台、ASMR、虚拟UP主、搞笑、日常、动物圈

**分区白名单**（候选池）：
- 人文历史、知识、社科、影视、纪录片（仅限解读类）、科技、财经、校园学习

**分配规则**：
- 随机抽 5 个分区，不重复
- 每池锁定一个分区，全流程只在该分区内搜索
- 历史记录每次运行的分区组合，避免短期内重复

### 2.3 每池独立流程

```
┌─ 单个池子的完整生命周期 ───────────────────────┐
│                                                  │
│  while 合格视频数 < 2 and 重试次数 < 上限(3):     │
│    ① 在该分区内搜索 15 条候选                     │
│    ② L1 过滤（时长、标题、内容类型）              │
│    ③ L2 打分（有字幕直接用，无字幕触发GPU转录）    │
│    ④ L3 打分（完整字幕分析）                      │
│    ⑤ 池内策展（选最高分 2 条）                    │
│    if 不够 2 条:                                  │
│      换搜索关键词/排序方式 → 重试                 │
│                                                  │
│  重试 3 次仍不够 → 接受实际数量（0~1条），不硬塞  │
│                                                  │
└──────────────────────────────────────────────────┘
```

**重试策略**：
- 第 1 次：按"最多播放"排序搜索
- 第 2 次：按"最新发布"排序搜索
- 第 3 次：更换分区内关键词（如从"历史"换为"朝代/制度/战争"）

### 2.4 GPU 转录调度：负反馈调节

5 个池的 L2 阶段都需要 GPU 转录，但 RTX 4050 只有 6GB VRAM，不能 5 池同时转录。

**调度策略**（复用现有 `gpu_monitor.py` 的 `VRAMGuard` + `AsyncTranscriber`）：

```
① 初始启动 1 个池的转录任务
② 实时监控 VRAM 使用率：
   - VRAM 使用率 < 75% 且有待转录任务 → 新增 1 池并行转录
   - VRAM 使用率 > 95% → 暂停新增，当前池排队等待
   - 某池转录完成 → 释放显存 → 等待池自动补位
③ 循环直到 5 池全部完成
```

这是一个经典的负反馈控制系统——显存就是被控变量，并行池数就是控制变量。不需要预设并行数，系统自动找到最优平衡点。

### 2.5 数据源升级：关注UP主 + 收藏夹

**第一阶段（种子用法，立即生效）**：

- 141 位关注的 UP 主 → 注入每个池的搜索种子：搜索时附带关注 UP 主的 uid，B 站搜索 API 会优先返回关联内容
- 40+ 收藏夹中的视频 → 提取这些视频的 UP 主 uid 和 BV 号，作为关联推荐和 UP 主蔓延的种子
- 每池种子 = 该分区内你关注/收藏过的 UP 主

**第二阶段（样本分析，后续迭代）**：

- 全量分析收藏夹视频的特征：UP 主分布、时长分布、话题分布、分区分布
- 用分析结果自动校准打分权重，替代手工设置的 `taste.topics`
- 精准识别你实际偏好（不是你以为的偏好）
